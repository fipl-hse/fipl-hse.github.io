Публикация лабораторной работы
==============================

.. contents:: Содержание
    :depth: 2


В данном документе описан порядок публикации лабораторной работы.
Предполагается, что на момент публикации лабораторной работы существуют следующие элементы:

- Текст лабораторной работы;
- Работающая имплементация.

Далее описаны шаги, необходимые для успешной публикации лабораторной работы.

1. Проверка имплементации в админе
----------------------------------

Удостоверьтесь, что при наличии лабораторной работы CI зелёный.
Этот этап включает проверку следующих параметров:

1. Покрытие тестами (coverage);
2. Наличие стабов;
3. Проверка кода линтерами;
4. Наличие UML-диаграммы в RST файле;
5. Спеллчек работает корректно и не выдаёт ошибок;

Чтобы проверить лабораторную работу на соответствие этим и другим параметрам,
можно использовать следующий скрипт:

.. code:: bash

   ./admin_utils/precommit.sh

2. Проверка текста в админе
---------------------------

Чтобы проверить текст перед публикацией, необходимо построить RST.
Скрипт для построения RST в том числе запускается в ``./admin_utils/precommit.sh``.

.. code:: bash

    sphinx-build -b html -W --keep-going -n . dist -c admin_utils

Далее файл ``dist/admin_utils/index.html`` открывается (например, с помощью
`расширения VSCode <https://marketplace.visualstudio.com/items?itemName=ritwickdey.LiveServer>`__)
для проверки текста, а также API.

Лабороторная проверяется на нескольких уровнях:

- Логика;
- Последовательность;
- Опечатки;
- Отображение изображений;
- Ссылки;
- Примеры;
- Докстринги (совпадение описания объектов с их названиями, как в тексте, так и в API).

3. Публикация в публичный репозиторий
-------------------------------------

Далее файлы лабораторной работы публикуются в публичный репозиторий.
Обновляются следующие места:

- Папка с лабораторной работой (стабы, тесты, текст,);
- ``README.rst``;
- ``pyproject.toml``
    - Пути для тестов (``tool.pytest.ini_options``);
    - Пути для isort (``src_paths``);
    - При необходимости overrides для заглушения ошибок mypy и pylint;
- ``project_config.json``;
- ``admin_utils/precommit.sh``.

С помощью ``admin_utils/precommit.sh`` проверяется целостность
лабораторной работы (выложеннных стабов, тестов, форматирования кода).

По результатам публикации в публичном репозитории пустой лабораторной
работы CI должен быть зелёным.


4. Проверка в приватном форке
-----------------------------

Создайте форк публичного репозитория.

В настройках форка нажмите ``Leave fork network``,
затем измените статус форка на приватный в блоке ``Change repository visibility``.

После того, как форк стал приватным, клонируйте его как VSCode проект.
Перед началом проверки лабораторной необходимо удалить собственный GitHub никнейм из
``project_config.json``, чтобы удостовериться в корректной работе ``PR name check``,
который пропускается для админов курсов.

Проверка лабораторной работы выполняется в отдельной ветке. Файлы лабораторной изменяются,
пушатся и просматриваются в формате Пулл Реквеста. Проверка должна проводиться для всех оценок
(0, 4, 6, 8, 10).

При необходимости пропустить проверку тестов для других лабораторных работ, обратитесь к
инструкции :ref:`ignoring-tests`.

5. Публикация документации на сайте
-----------------------------------

Далее необходимо опубликовать лабораторную работу на сайт. 

В `репозитории сайта <https://github.com/fipl-hse/fipl-hse.github.io>`__ стабы хранятся в папке
с соответствующим лабораторной работе названием.

.. code:: text

    +-- fipl-hse.github.io
        +-- lab_1_classify_profile
            +-- __init__.py
            +-- main.py

Текст хранится в разделе с документацией в папке.

.. code:: text

    +-- fipl-hse.github.io
        +-- source
            +-- docs
                +-- index.rst
                +-- archived_courses
                    +-- index.rst
                    +-- 2025_2026
                        +-- index.rst
                        +-- labs_2025
                +-- labs_2026
                    +-- index.rst
                    +-- general_info.rst
                    +-- lectures_content.rst
                    +-- labs
                        +-- index.rst
                        +-- lab_1_classify_profile
                            +-- assets
                                +-- description.png
                            +-- lab_1.rst
                            +-- lab_1_classify_profile.api.rst

При публикации лаборатолрной работы файл с текстом выкладывается в соответствующую папку.
На примере лабораторной работы ``lab_1_classify_profile``:

- ``README.rst`` -> ``lab_1.rst``
- ``lab_1_classify_profile.api.rst`` -> ``lab_1_classify_profile.api.rst``
- Папка ``assets`` содержит любые изображения, на которые ссылается текст.

Также необходимо добавить ``labs/lab_1.rst`` в ``labs_2026/labs/index.rst``.

Если курсы предыдущего года ещё не архивированы, перенесите их в соответствующую папку ``archived_courses``.
Обновите ``archived_courses/index.rst`` и ``docs/index.rst``.
При переносе может понадобиться обновить ссылку на лекции соответствующего года:

.. code:: text

    `здесь <https://fipl-hse.github.io/docs/llm_2025/lectures_content.html>`__ -> :ref:`lectures-content-llm-label-2025`.


После добавления файлов, нужно построить сайт:

.. code:: bash

    python tools/docs_generator/build_documentation.py


Проверьте добавленную лабораторную на предмет сломанных изображений, ссылок
и форматирования. Построенный сайт будет лежать в ``source/build/index.html``.

После того, как обновление было замёржено, лабораторная работа появится
`на сайте <https://fipl-hse.github.io/>`__.

6. Сообщение в чате курса
-------------------------

После полной публикации лабораторной работы, необходимо сделать анонс в чате (паблике) курса.
В анонсе нужно упомянуть:

- Необходимость обновления форков;
- Необходимость сделать ``git pull``;
- Наличие документации на сайте;
- Дедлайн.

Если студентов необходимо обновить вручную, воспользуйтесь инструкцией :ref:`fork-update`.
В таком случае, необходимо уведомить студентов об успешном обновлении форков.

..
    Синхронизация админа и сайта с помощью DOCSYNC
    ----------------------------------------------

    Инструмент DOCSYNC, работающий через CI (external_pr.yml), позволяет перенести файлы из
    админского репозитория в сайтовый репозиторий. Следующие шаги необходимы для успешной работы инструмента.

    1. Заполнить список переносимых файлов в ``project_config.json``:

    .. code:: python

        [
            {
                "source": "lab_1_classify_profile/README.rst",
                "target": "source/docs/labs_2026/labs/lab_1_classify_profile/lab_1.rst"
            },
            {
                "source": "README.rst",
                "target": "source/docs/labs_2026/general_info.rst"
            }
        ]


    2. Запустить скрипт одним из способов:

        - Оставить комментарий ``[SYNC_TO_CHILD]`` в Пулл Реквесте;

        - Сделать мёрж в мастер с меткой ``[DOCS]`` в названии коммита.

    3. Перейти в репозиторий сайта, проверить и замёржить автоматически-созданный Пулл Реквест.
